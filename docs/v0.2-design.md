# Preflight v0.2 — Design Document

## Status

Draft, in progress. This document captures design decisions as they are made. Sections marked OPEN are not yet designed. Do not implement from this document until it is marked complete.

## Source of this design

This design responds to the PR 12 issues inventory (docs/pr12-issues-inventory.md, commit 5339ee4) and its bucketing (docs/pr12-issues-bucketed.md, commit 1dea5ea). The bucketing found 63% of PR 12 issues are framework structural gaps (Bucket A), 20% are CPSL-specific requirements (Bucket B), 17% are framework-shaped CPSL needs (Bucket C). v0.2 addresses the framework-level work (A + C); Bucket B becomes content teams declare once the framework has somewhere to put it.

## The core reframing

Reading the existing CLAUDE.md (the CPSL team contract, 519 lines) surfaced that the document describes framework enforcement that does not actually happen at runtime. It mandates the Stage 1 gate, the four mechanical hooks, 96% coverage, and a definition-of-done checklist — but PR 12 showed none of these enforced anything. The hooks didn't fire, coverage wasn't gated, the definition-of-done didn't block push. The gap between what CLAUDE.md describes and what the framework does at runtime IS the framework's core problem (this is roll-up r12 from the bucketing made concrete).

Additionally: the existing CLAUDE.md actively contributed to the PR 12 wire-contract failure. Its guidance — "Migrate the intent, not the literal code" and "Optimize during migration: async/await" — licensed the agent to change result codes and alter async semantics, because the document gave modernization guidance with no counterweight requiring external-contract preservation. The agent followed the contract; the contract was incomplete.

v0.2 therefore has two workstreams: (1) make CLAUDE.md's existing enforcement promises real, and (2) add the wire-contract preservation capability the contract is missing.

## Part A — The Team Contract (DESIGNED)

### What it is

A declaration of what a given team's migration requires. Per-team, not per-migration. One contract per consuming team; all of that team's migrations inherit from it. Service-specific details live in the comparison surfaces the contract declares, not in the contract itself.

### Where it lives (DECIDED)

The contract is NOT a separate file. It is a new, high-precedence SECTION added to the existing CLAUDE.md. The existing CLAUDE.md is already designated "the team contract" in its own first line; v0.2 adds the missing wire-contract section to it.

Critical: this new section must have explicit precedence over the existing modernization guidance in CLAUDE.md. Where the wire-contract section conflicts with guidance like "migrate the intent, not the literal code" or "optimize during migration," the wire-contract section wins. The precedence must be stated in the section itself, e.g.: "Where this section conflicts with the modernization guidance elsewhere in this file, this section governs. Modernize implementation freely; preserve external contract exactly."

### The three parts (DESIGNED)

**Part 1 — Success criteria.**

Declarative statements of what must be true at migration completion. Not how to verify — just what must be true. For the CPSL team, the success criterion is wire-format and result-code parity: every result code the legacy emits must appear in migrated output with identical semantics; response messages, payload field names and shapes, HTTP status codes per error condition, and version-based routing behavior must be preserved.

**Part 2 — Comparison surfaces.**

For each success criterion, which legacy artifacts define the truth. For the CPSL wire-parity criterion, the comparison surfaces are the legacy controller PLUS repository PLUS auth filter — the full transitive scope, not just the entry-point controller. (PR 12 failed precisely because discovery read only the controller, 183 lines, and missed the repository, 500 lines, where 80% of the wire contract lives.) Version-based routing logic is a first-class comparison surface for CPSL specifically, because CPSL code is heavy in version-based routing.

**Part 3 — Constraint handling (three-way).**

Every change the migration makes falls into one of three categories, determined by two independent tests:

**PRESERVE EXTERNAL CONTRACT** — things a caller of the API observes. Test (axis 1): "Would a caller's existing code break or behave differently if pointed at the migrated service instead of the legacy service, assuming nothing in the caller is changed?" If YES → preserve exactly. This covers result codes, response messages, payload field names and shapes, HTTP status codes per error condition, version-based routing logic, endpoint URLs and HTTP methods.

**MODERNIZE INTERNAL IMPLEMENTATION** — things a caller does not observe. Same axis-1 test, answer NO → modernize freely. This covers sync/async patterns, fire-and-forget vs await, HTTP client library choices, JSON serialization library, DI container patterns, logging frameworks, exception-handling idioms (as long as external HTTP status + ResultCode behavior is preserved), configuration patterns, test framework choices.

Caveat: JSON library swaps (e.g., Newtonsoft → System.Text.Json) are modernize-freely at the code level BUT require compatibility verification of the produced output, because the two libraries differ subtly in null handling, casing, and date serialization. A library swap is not safe by virtue of being internal; the output must be verified to match.

**SURFACE AS WORK** — an independent axis. Test (axis 2): "Does this change require additional engineering artifacts beyond the application code itself — database schemas, infrastructure, downstream service contracts?" If YES → the framework does the work visibly, producing real artifacts, never placeholders. This is NOT a request for human permission; it is the framework doing the work honestly. A single change can be MODERNIZE-FREELY on axis 1 AND SURFACE-AS-WORK on axis 2 simultaneously (the DB migration is exactly this: invisible to the caller at the wire level, but visible engineering work requiring schema artifacts).

### The framework's job for Part 3 (DECIDED)

The framework must REASON about each constraint and decide correctly — not merely detect-and-flag, not merely preserve-by-default. The framework needs to understand why each constraint exists and what the right call is. This is a deliberately high bar, chosen because the team's position is that the framework must be rock-solid autonomously.

### No human gates (DECIDED)

There is deliberately NO "human-required decisions" part. The team rejected mid-flow human approval gates. The framework must operate end-to-end autonomously. If the framework cannot autonomously preserve external contract and surface additional work correctly, that is a framework defect to fix — not a reason to add a human checkpoint. Visibility into what the framework decided comes through the decisions-log (see OPEN section), not through asking permission.

### The database faithfulness rule (DECIDED)

When persistence-layer migration is needed (e.g., SQL Server → PostgreSQL), the framework must port faithfully with EXACT identifier fidelity: same database name, same table names, same column names, same data types — no modifications, no schema "improvements," no renamed identifiers. The framework navigates the legacy persistence artifacts and produces equivalent target artifacts (e.g., PostgreSQL DDL and PL/pgSQL functions) using identical names.

PR 12 failed this completely: it invented five PostgreSQL stored-function names that exist nowhere, with no DDL, no real extraction. That is the exact failure this rule prevents.

### The legacy-DB-unreachable workflow (DECIDED)

The CLI cannot directly connect to the legacy SQL Server database. Therefore the framework's "surface as work" capability for DB migration has two acceptable modes:

- **Mode 1 (CLI cannot reach legacy DB — the expected case):** the framework produces a precise, concrete artifact listing exactly what must be fetched from the legacy DB — table names, stored-procedure names, column names with data types — formatted as either a runnable extraction script or a step-by-step extraction guide. It hands this to the human, who fetches and returns the output. The framework then converts the returned legacy artifacts to faithful target-DB equivalents.
- **Mode 2 (CLI can reach legacy DB, if such a capability exists):** the framework fetches and converts autonomously in one pass.

Critically: the framework must be HONEST about which mode applies. It must never pretend it performed Mode 2 (autonomous fetch) when it actually cannot reach the DB — that pretense is exactly what produced PR 12's invented function names.

**Derived capability need:** This implies the framework needs a new discovery capability distinct from code-coupling analysis: "legacy data-access surface extraction" — reading the legacy code's data access patterns (SQL strings, stored-proc invocations, ADO.NET parameter declarations) to infer which DB tables/sprocs/columns the service touches, BEFORE it can produce the fetch list. The current discovery-analyst produces a code dependency map (dependency-map.json); persistence-bearing services also need a data-access-surface map. This capability is DESIGNED-IN-PRINCIPLE, implementation OPEN.

## Part B — The Two Workstreams (DECIDED structure, details partially OPEN)

v0.2 splits into two parallel workstreams that reinforce each other:

**Workstream 1 — Make CLAUDE.md's existing promises real.**

The framework already describes enforcement it does not deliver. This workstream makes the description true: the mechanical hooks actually fire, the Stage 1 gate actually gates, the 96% coverage actually blocks push, the definition-of-done actually prevents push when unmet. This maps to Bucket A roll-ups, especially r03 (hooks configured but inert), r04 (no hook observability), r06 (sub-agent architecture partially realized), r15 (discovery output not enforced).

**Workstream 2 — Add the wire-contract preservation capability.**

The framework cannot currently preserve or even detect wire-contract drift. This workstream adds: the three-part contract section in CLAUDE.md (DESIGNED above), spec extraction (OPEN), the parity gate (OPEN), the decisions-log (OPEN), and the DB faithfulness capability (DESIGNED in principle, implementation OPEN). This maps to Bucket C and the roll-ups r01 (team-contract artifact), r02 (spec extraction), r05 (result-code comparison), r07 (done ≠ contract-preserved), r09 (decisions-log).

**Ordering dependency (IMPORTANT):**

The two workstreams can be DESIGNED in parallel, but there is a validation dependency: Workstream 2's parity gate cannot actually fire until Workstream 1's hook-activation work is done. A parity gate plugged into an enforcement layer that doesn't fire would be just as inert as the current hooks. Therefore: hook activation (Workstream 1, r03) is a prerequisite for the parity gate (Workstream 2, r07) to be VALIDATED, even if both are designed concurrently.

## Part E — Foundational finding: silent component-load failure (r16)

Status: NEW FINDING (post-design, from a bootstrap diagnostic attempt). This finding is FOUNDATIONAL — it sits beneath the two workstreams and reframes their ordering.

### The finding
When a named framework component fails to load or engage, the framework silently degrades to general-agent behavior and produces output that is indistinguishable from the real component running. No error is raised. No "component not found" signal reaches the operator.

Confirmed three times:
- i14 (PR 12): the migrate skill referenced subagent_type "discovery-analyst" which did not exist in the agent registry; the framework silently fell back to a general-purpose agent.
- i32 (PR 12): hooks configured via run-hook.cmd produced no diagnostic output; whether they fired or not was unknowable.
- Bootstrap diagnostic attempt: an invocation of /preflight:bootstrap in Validate mode did NOT load the bootstrap skill. The agent confirmed, when asked directly, that it produced the validation "from my own reasoning about what bootstrap validation should do, without the skill file being loaded." The output was a detailed, file-grounded, plausible validation report — indistinguishable in shape from a real bootstrap run.

### Why this is foundational
Every other v0.2 capability assumes its components actually run when invoked. If invocation is unreliable and failure is silent, no component's self-report can be trusted. "Running preflight" and "an agent improvising what preflight would do" are currently indistinguishable from the operator's seat. This undermines every claim the framework makes about itself.

### r16 (new roll-up)
The framework silently degrades to general-agent behavior when a named component fails to load, with no signal to the operator. Components must fail LOUDLY (explicit error: "component X failed to load"), never improvise a substitute. r16 is a PREREQUISITE for r03 (hook activation) and r04 (observability): there is no point making hooks fire if you cannot tell whether they fired, and no point adding observability if the underlying failure mode is silent substitution rather than honest error. r16 rolls up i14, i32, and the bootstrap diagnostic finding.

### Leading hypothesis (UNVERIFIED, to be tested)
A single root cause may explain i14, i32, and the bootstrap finding: the preflight plugin may not actually be loaded in these CLI sessions at all. If the plugin is not loaded, then none of preflight's skills, agents, or hooks are available, and every apparent "run" of a preflight component has been the agent improvising. This is the leading hypothesis and is testable. It must be tested before further v0.2 capability design, because there is no point designing capabilities for a plugin that does not load.

### Re-labeling the bootstrap diagnostic
The CLAUDE.md validation report produced during this diagnostic is NOT a bootstrap validation. It is a general-agent diagnostic of CLAUDE.md. Its findings about the file are still useful as input to the eventual CLAUDE.md rewrite (notably: the IS/SHOULD-BE conflation, two HIGH-severity contradictions — "migrate the intent" and "optimize during migration" — the stale Terraform-vs-CDK rubric §3, and the dead rubric §17 reference). But it must not be cited as evidence about bootstrap's behavior or judgment quality, because bootstrap never ran.

## Part F — Planned validation step: three-way CLAUDE.md validation against AccountLookup

Status: PLANNED, not yet executed. To be run after the plugin-loading hypothesis is tested.

The AccountLookup service is a completed, end-to-end CPSL migration (code, tests at ~96%, CDK infrastructure) and is CLAUDE.md's designated reference service. It is therefore ground truth for "what a real, complete, correct CPSL migration actually looks like."

This enables a three-way validation of CLAUDE.md:
- What CLAUDE.md says a migration requires
- What the legacy service actually has (wire contract, DB surface)
- What AccountLookup actually produced (the real, working migration)

Classification:
- CLAUDE.md says X is required, but AccountLookup did not do X and is fine → X is noise CLAUDE.md can drop.
- AccountLookup did Y, but CLAUDE.md never mentions Y → CLAUDE.md has a gap.
- CLAUDE.md, legacy, and AccountLookup all agree → load-bearing, keep.

Early hints already surfaced (from the general-agent diagnostic): CLAUDE.md requires per-service MIGRATION_PATTERNS.md but the reference service has none; CLAUDE.md describes <Service>StackProps.cs as the pattern but AccountLookup uses UalStackProps from a shared package. Both are "CLAUDE.md says X, the gold-standard service does Y" discrepancies — exactly what this validation is for.

This validation informs the eventual one-pass CLAUDE.md rewrite (trim noise + fix contradictions + add wire-contract section), which remains deferred until the wire-contract section is designed.

## Part G — ROOT CAUSE: the plugin was never installed as a plugin

Status: CONFIRMED via mechanical diagnostic. This is the central finding of the post-PR-12 investigation. It is the single root cause beneath r16 and beneath a large fraction of the Bucket A inventory. It re-scopes the entire v0.2 effort.

### The mechanical truth
A direct, mechanical diagnostic of the session environment found:
- The plugin directory exists on disk as a symlink: ~/.claude/plugins/preflight → code-forge (verified).
- The plugin has NO manifest: ~/.claude/plugins/preflight/.claude-plugin/manifest.json does not exist. No config.json either. The .claude-plugin/ directory is effectively empty.
- The plugin is NOT registered in ~/.claude/settings.json — there is no plugins key.
- Therefore the plugin is not loaded as a plugin. It is a directory on disk that nothing loads as a unified plugin entity.

### Why some skills appeared to work
The preflight skills that appeared functional (fix-and-close, migrate-service, systematic-debugging) work through a SEPARATE, ad-hoc mechanism: individual symlinks in ~/.claude/skills/ that load them as user-skills, one by one. This is NOT plugin loading. It is a manual workaround that masked the fact that the plugin itself was never activated.

### What this explains (single root cause for many symptoms)
- bootstrap never ran (the recent diagnostic): bootstrap was never symlinked into ~/.claude/skills/, and the plugin that would load it isn't loaded. /preflight:bootstrap could not resolve.
- i14 (discovery-analyst not in registry): the sub-agent is defined on disk (agents/discovery-analyst.md) but is NOT a registered subagent_type, because the plugin that registers agents isn't loaded. Confirmed: the session's available agent types do NOT include discovery-analyst or implementer.
- i30 (only 2 of 4 sub-agents invoked): implementer is also not registered. "Not dispatched" was not a choice — the agent type does not exist in the registry.
- i17, i18, i19, i22, i24, i32, i45, i46 (hooks inert / unconfirmed): hooks live in the plugin and require plugin loading to register. The plugin isn't loaded, so no hook was ever wired or fired.
- r03 (hooks configured but inert), r06 (sub-agent architecture partially realized), r16 (silent component-load degradation): all downstream of this single root cause.

Only code-reviewer and copilot-review-loop (the renamed external-review-handler) are actually in the agent registry — these are the only sub-agent components that were genuinely available.

> **Later clarification (post-v0.7.5):** this paragraph records the PR-12-era state. The agent is now named **`external-review-handler`** across the live framework; `copilot-review-loop` is a dead identifier surviving only in this historical narrative (verified: no skill/agent `subagent_type` references it, and the v0.7.6 installer prune removes any `copilot-review-loop.md` left in a consumer from an older install). Left in place above to preserve the original post-mortem record rather than rewrite history.

### What this reframes about PR 12
PR 12 was not "the framework ran and produced a wire-contract-broken result." PR 12 was a general-purpose agent, with a few manually-symlinked skill files loaded as context, improvising a migration while appearing to run a framework that was not actually loaded. The missing agents, missing hooks, and missing enforcement were absent because the framework was never installed — and the framework silently degraded rather than signaling the absence. The wire-contract break and silent DB swap occurred in the absence of any enforcement machinery, with no signal to the operator that the machinery was not present.

### Re-scoping the bucketing
The Bucket A inventory now splits into two distinct classes:

CLASS 1 — Resolves to "install the plugin correctly." A large set of Bucket A items are symptoms of the plugin not being loaded, and are expected to resolve once the plugin is installed with a manifest, registered in settings, and its components (all skills including bootstrap, all four sub-agents, all hooks) verified to register. This includes: i14, i17, i18, i19, i22, i24, i30, i32, i45, i46, and roll-ups r03, r06, and the mechanism of r16.

CLASS 2 — Genuine capability gaps that survive plugin installation. These do NOT resolve by loading the plugin, because the capability genuinely does not exist anywhere in the framework: the wire-contract preservation work (r01, r02, r05, r07), the DB faithfulness capability and data-access-surface extraction, the decisions-log (r09), the mid-flow surfacing (r11), the CLAUDE.md contradictions ("migrate the intent"), and the CLAUDE.md IS/SHOULD-BE conflation. This class is the real v0.2 design work, and the design done so far (Parts A-D) stands.

### Re-scoped v0.2 ordering
1. FIRST (new top priority): install preflight as an actual plugin. Create the manifest, register in settings, verify all skills (including bootstrap) load via the plugin rather than ad-hoc skill symlinks, verify all four sub-agents register as invocable subagent_types, verify hooks register and fire. Add loud-failure behavior so component-load failure is signaled, never silently improvised (this is r16's fix). The correct installation mechanism must be verified against official Claude Code plugin documentation before attempting the fix — not assumed.
2. THEN: validate the install actually worked (components resolve, a hook fires, a sub-agent dispatches).
3. THEN: the Class 2 capability design resumes (spec extraction, parity gate, decisions-log, DB faithfulness, CLAUDE.md rewrite).

### The meta-lesson
The framework cannot report what it is. Every prior "the framework ran X" observation was unreliable because the framework silently degrades. This root cause was found only by direct mechanical inspection prompted by operator skepticism. All framework self-reports must be mechanically verified, not taken at face value.

## Part H — spec-analyst: behavioral spec extraction (r02) — DESIGNED

Status: DESIGNED (conversational design, this session). This is the framework's behavioral extraction capability — the thing whose absence caused PR 12's wire-contract failure.

### The root cause this fixes
A read-only investigation of discovery-analyst confirmed: discovery-analyst reads the right files (it found and mapped the repository in PR 12) but extracts ONLY structural details (dependencies, coupling, package versions). It is blind to behavior by design — its instructions never mention result codes, HTTP statuses, response shapes, validation logic, or wire contracts. PR 12's dependency-map.json captured the repository's structure and zero of its behavior. The framework has NO behavioral extraction capability anywhere. spec-analyst fills this gap.

### Identity
A NEW read-only sub-agent, single purpose: extract the forensic behavior spec from the legacy comparison surfaces. Never writes service code, never generates the migration. Dispatched as a sub-agent, produces an artifact, returns DONE. Parallel in pattern to discovery-analyst. Chosen as a separate sub-agent (not an extension of discovery-analyst) because behavioral extraction is a fundamentally different cognitive task from structural mapping — different instructions, different output schema, different completeness check.

### Flow position
Runs AFTER discovery-analyst, BEFORE code generation:
discovery-analyst → dependency-map.json (structural: what calls what)
spec-analyst → behavior-spec.json (behavioral: what the wire contract is)
[autonomous — no human gate, per the no-gates decision]
code generation → Stage 1 review (code quality) → parity gate (compares migration vs behavior-spec) → push

spec-analyst CONSUMES discovery-analyst's dependency-map to know where the declared comparison surfaces live, then reads them deeply. The two passes are not redundant: discovery-analyst finds WHERE the surfaces are; spec-analyst extracts WHAT they do.

### What it reads
Parameterized by the team contract's Part 2 (comparison surfaces). For CPSL: controller + repository + auth filter, full transitive scope. spec-analyst reads the FULL IMPLEMENTATION of every declared surface — every validation branch, result-code assignment, status set, response-field write, routing decision. Not signatures, not coupling (that is discovery-analyst's job) — the actual behavioral logic.

### What it produces: behavior-spec.json
Behavior-by-behavior, structured for machine comparison (the parity gate will diff migrated output against it row-by-row). Each row:
- behaviorId (stable identifier)
- inputCondition (e.g., "request.Version is null or empty")
- expectedOutput (resultCode, resultMessage, httpStatus, responseShape)
- citation (exact legacy source: file:line:method)
- surface (which comparison surface it came from)

Covers every behavior the contract cares about: each validation rejection (the 8-step chain), each version-routing branch (V1/V2/SkipPhoneCapability), each auth rejection (W0001/E0001 with WWW-Authenticate), each downstream-failure path (the 400-override), the success case (E0000), timing semantics (SlideToken fire-and-forget).

### Anti-faking: BOTH mechanisms (decided)
Mechanism A — Citation-grounding (mandatory): every behavior row MUST cite exact legacy source (file:line:method). A row without a citation is invalid — it means the analyst inferred a behavior rather than reading it. This ensures every row the analyst WRITES is real. (PR 12 invented S0000 and W0024 with no source basis — this prevents that.)

Mechanism B — Source-scanning completeness check (loud failure): after spec-analyst produces the spec, a mechanical scan of the comparison surfaces finds every behavior-token and verifies each appears in the spec with a citation. A behavior present in source but absent from the spec FAILS LOUDLY (e.g., "W0006 found at CPSLTokenRepository.cs:88 but absent from behavior-spec — extraction incomplete"). This ensures the analyst MISSED nothing. This is the mechanism that directly catches PR 12's actual failure: missing codes W0002-W0008 (present in the repository, absent from the migration).

Why both: citation-grounding ensures every row written is real; the completeness check ensures none were missed. PR 12's failure was MISSING codes, not inventing them — so the completeness check is the one that directly addresses the actual failure. Both together close both failure modes.

### Contract addition required (NEW)
Mechanism B requires the team contract (Part 2, comparison surfaces) to also declare HOW TO RECOGNIZE A BEHAVIOR in the declared surfaces — so the completeness scan knows what to look for. For CPSL: result codes match the pattern [WE]\d{4}; HTTP statuses are set via specific patterns; response shapes are specific types. This is a small per-team declaration, cheap for a team doing wire-contract-sensitive migrations (they know their own code patterns), and it keeps the completeness check parameterized rather than CPSL-hardcoded. This addition folds into Part A, Part 2 of the team contract.

### DB extraction: separate artifact (decided)
The DB-faithfulness rule's legacy-database-surface extraction (table names, column names, stored procedures, data types) lives in a SEPARATE artifact — data-access-surface.json — NOT in behavior-spec.json. Reason: different kind of behavior (persistence vs wire), different consumer (the DB-migration workflow vs the parity gate), different lifecycle. Keeping them separate keeps each artifact single-purpose. Whether spec-analyst also produces data-access-surface.json, or a distinct extractor does, is OPEN — but the artifact is separate either way.

### OPEN sub-items
- Whether spec-analyst produces data-access-surface.json itself, or a distinct DB-extraction step does.
- The exact format of the completeness-check scan (how behavior-token patterns from the contract are applied to the source).
- These are implementation details, deferred to build time.

## Part I — The parity gate: universal behavior-preservation gate (r07) — DESIGNED, including hook insertion grounded in real code

Status: DESIGNED (conversational design, this session). This is spec-analyst's consumer — the gate that enforces the contract. It was the capability missing in PR 12 (there was a Stage 1 code-quality gate but NO gate checking contract preservation). The hook insertion below is grounded in reading the actual hook scripts, not assumptions.

### Scope: universal, not migration-specific (decided, widened from initial framing)
The gate is NOT a migration-only parity check. It is a general behavior-preservation gate covering: migration, refactor, bug fix, enhancement, and new service development. It is ONE gate with ONE mechanism; the only thing that varies by work type is the SOURCE of the contract (the source of truth being preserved):
- Migration → contract = legacy service's extracted behavior (behavior-spec.json from spec-analyst)
- Refactor → contract = current service's behavior captured before the change
- Bug fix → contract = current behavior MINUS the specific bug being fixed
- Enhancement → contract = current behavior (new behavior is additive, exempt from "must match")
- New service → contract = the team's declared/intended spec (no extraction; declared, not extracted)

### Stack-independence (decided)
The gate is a stack-NEUTRAL comparison engine. It contains ZERO stack-specifics — no .NET-isms, no result-code patterns, no HTTP idioms. All stack-specific knowledge (what a behavior looks like, what the comparison surfaces are) lives in the per-team contract. The gate reads those definitions from the contract. The same engine serves a .NET team, a Java team, a Python team — each declares its own behavior-patterns and surfaces; the engine just diffs structured behavior-specs. This is the same parameterization discipline used throughout (contract is per-team, spec-analyst is contract-parameterized).

### The mechanism: one gate, four parts
1. Contract source resolver — picks the source of truth by work type (the only work-type-aware part). Reuses spec-analyst's extraction for migration/refactor/bugfix/enhancement (all need "extract behavior from code"); new-service development skips extraction (spec is declared).
2. Comparison engine (stack-neutral) — diffs two behavior-specs (the contract source-of-truth, and the post-change extraction) row by row, using the behavior-patterns the contract declares. Produces: matches, mismatches, missing behaviors (in contract, absent from change), new behaviors (in change, absent from contract).
3. Intended-change filter — not every difference is a violation. Differences matching the DECLARED intended change are allowed; unintended differences are violations. Migration/refactor intent is usually "preserve all" (any difference = violation). Bug fix declares which behavior(s) are the intended fix (those allowed to differ). Enhancement declares new behaviors as additive (exempt). This filter is the parameter that lets one gate serve all work types.
4. Block-and-learn loop — violations (unintended differences) trigger a fix-loop: block push → surface violations → fix → re-extract → re-compare → until clean. Every violation caught is capture-worthy: it feeds the same capture/learning mechanism that strengthens the rubric, so a behavior-drift caught on one piece of work strengthens detection on the next. This is the third gate (alongside Stage 1 quality and Stage 2 Copilot) that makes "validate everything before push" true.

### Baseline capture: precedence chain c → b → a (decided)
For work on existing services (refactor/bugfix/enhancement), the gate needs the baseline contract — the service's behavior before the change. Three methods form a precedence chain, best-to-fallback, and the gate ALWAYS has a baseline:
- (c) Persistent maintained behavior-spec — PRIMARY. Every service carries a behavior-spec.json in its repo, produced at creation (new-dev declares it) or migration (spec-analyst extracts it), deliberately updated when behavior is MEANT to change. The gate uses this stored spec as the contract. Ideal state — the spec is a living, permanent artifact the gate protects forever.
- (b) Extract from git HEAD — FALLBACK when no stored spec exists. For a service without a maintained spec, the gate extracts the baseline from the last committed version (git HEAD before the change) and compares the working tree against it.
- (a) Capture-on-start — FALLBACK when git HEAD isn't a clean baseline (dirty tree, work already in progress). Capture current behavior at the moment work is declared to start, freeze it, then allow editing.
Precedence: use (c) if a maintained spec exists; else (b) from git HEAD; else (a) capture-on-start. CRITICAL PROPERTY: (b) and (a) are also the ON-RAMP to (c) — the first time the gate extracts a baseline for a spec-less service, it writes that extraction as the service's new persistent behavior-spec, bootstrapping the service toward the (c) ideal. Every service eventually converges to a maintained spec.

### Hook insertion (Q3) — GROUNDED IN ACTUAL HOOK CODE, not assumptions

Stale or missing evidence → exit 1 (blocks push with stderr message). Cannot be bypassed by prompt manipulation — it is a mechanical hook checking files on disk against git state.
- write-gate-evidence writes those files: takes a gate-name (validated against tests-pass|stage1-clean|map-validated), writes .preflight/gate/<name> with GATE=, HEAD=, TIMESTAMP=.

## Part J — ROOT CAUSE #2: run-hook.cmd passes the wrong argument to every input-taking gate (CONFIRMED via traces)

Status: DIAGNOSIS COMPLETE, triple-confirmed by bash trace. FIX DEFERRED to next session (the fix touches run-hook.cmd, which every hook depends on, and has cmd-quoting hazards on JSON input — it deserves careful, fresh attention).

### The finding
The pre-push gate fires but does not block. A throwaway commit with no gate-evidence files was pushed successfully to the real remote when it should have been blocked — confirming inventory item i18 is NOT merely a plugin-loading problem. The plugin is now loaded (confirmed) and the PreToolUse:Bash hook fires (confirmed: debug log line 310, "Slow PreToolUse hooks: 6714ms for Bash (1 hooks)"), yet the push still succeeded.

### The mechanical cause (proven by trace, not inferred)
run-hook.cmd forwards the hook NAME into the gate script's positional arguments, so the script reads $1 = the hook name instead of the actual tool input.

The gate script pre-push-gate-check does: TOOL_INPUT="${1:-}". It expects $1 to be the git command. But run-hook.cmd's argument forwarding (Unix line: exec bash ".../$1" "$@" where "$@" still includes $1 the hook name; Windows line: bash "%SCRIPT%" %* where %* includes the hook name) passes the hook name through as the script's $1.

Bash trace evidence (run via run-hook.cmd path):
  + TOOL_INPUT=pre-push-gate-check
  + COMMAND=pre-push-gate-check
  + echo pre-push-gate-check
  + grep -qE '(^|&&|\|\||;)\s*git\s+push'
  + exit 0
The grep searches the string "pre-push-gate-check" for "git push", finds nothing, exits 0 (pass-through). The actual git command never reaches the grep.

### Proof the gate logic itself is correct (target behavior verified)
When pre-push-gate-check is invoked DIRECTLY with the actual command as $1 (bypassing the wrapper), it works perfectly — bash trace:
  + TOOL_INPUT='git push -u origin throwaway'
  + grep matched → exec bash pre-push-gate → BLOCKED: Test suite has not run. → exit 1
So: pre-push-gate works (Test A: blocks, exit 1), run-hook.cmd propagates exit codes correctly (Test B: blocks, exit 1), and the gate logic is sound. The ENTIRE bug is that the wrapper feeds the script the hook name instead of the command.

### Hypotheses eliminated by testing (recorded so they are not re-attempted)
- Exit-code propagation in the wrapper — RULED OUT (Test B returned exit 1 through the wrapper).
- Regex-vs-JSON-wrapped-input — RULED OUT (the script handles raw "git push" correctly; the problem is upstream of the grep — the wrong argument arrives).
- CRLF line endings — RULED OUT (clean -x trace, no stray \r).

### Scope of impact (this is why it matters)
This single wrapper bug breaks EVERY gate that reads $TOOL_INPUT through run-hook.cmd:
- pre-push-gate-check "$TOOL_INPUT" → reads hook name → never blocks pushes (i18)
- bootstrap-write-gate "$TOOL_INPUT" → reads hook name → never gates CLAUDE.md writes
- coupled-edit-gate "$TOOL_INPUT" → reads hook name → never gates coupled edits (i19)
- rubric-validity-gate "$TOOL_INPUT" → reads hook name → never gates Stage 1 dispatch
All four input-taking gates broken by one wrapper bug. This explains inventory items i17, i18, i19 far more completely than "plugin not loaded" did.

### Two independent root causes for the dead enforcement layer — both now identified
1. The plugin was never installed (found and fixed earlier this session: bootstrap SKILL.md YAML typo + plugin not loaded; fixed via the quote fix and claude --plugin-dir; components now register, hooks now fire — all confirmed).
2. run-hook.cmd passes the hook name into the gate scripts' $1 (found and confirmed now; FIX DEFERRED).
Both had to be fixed for the gates to actually fire AND block. #1 fixed firing. #2 (pending) fixes blocking.

### The fix (DESIGNED, NOT YET APPLIED — next session)
run-hook.cmd must drop the hook name before forwarding the remaining arguments to the gate script.
- Unix line: capture and shift the hook name — e.g. hook="$1"; shift; exec bash ".../$hook" "$@"
- Windows branch: forward only arguments AFTER the hook name (not %*). CAUTION: the TOOL_INPUT contains spaces, quotes, and JSON; cmd argument reconstruction mangles these easily. This is the delicate part and the reason the fix was deferred to a fresh session.
- OPEN sub-question to resolve before fixing: whether Claude Code passes tool input as an ENVIRONMENT VARIABLE (in which case the scripts could read $TOOL_INPUT from the environment directly, sidestepping cmd argument-forwarding entirely — a more robust fix) versus only as a positional argument. This must be disambiguated (one instrumented test: log run-hook.cmd's args and environment on a real push, then revert) before choosing the fix shape.
- After the fix: re-verify end-to-end with the throwaway-branch push test — the gate must actually BLOCK a real push when evidence is missing, not merely receive the right argument in isolation.

### Verification method that found this (for reuse)
The throwaway-branch test: create a throwaway branch, make a real commit, confirm no .preflight/gate/ evidence exists, attempt to push it in a debug --plugin-dir session, check whether the gate blocks. A real pushable commit is required — "Everything up-to-date" produces an ambiguous result. Clean up the branch (local and remote) afterward regardless of outcome.

## Part K — CORRECTION to Part J: the real mechanism is stdin JSON, not positional-argument forwarding

Status: Part J's ROOT CAUSE MECHANISM WAS WRONG. This part supersedes it. The real mechanism is confirmed by official documentation AND by direct mechanical test. The fix is different from, and SAFER than, what Part J proposed.

### What Part J got right vs wrong
RIGHT: the gates fire but do not block; the gate scripts end up with $1 = the hook name, not the command; all four input-taking gates are affected; this explains inventory items i17/i18/i19.
WRONG: Part J attributed the cause to run-hook.cmd forwarding the hook name into the script's positional arguments, and proposed fixing run-hook.cmd's argument-passing. That mechanism is incorrect, and that fix would NOT have worked.

### The real mechanism (confirmed authoritative + mechanical)
Claude Code passes tool input to PreToolUse hooks via STDIN as a JSON object — NOT as positional arguments, NOT as an environment variable.

Documentation evidence (cited): the official hook test helper pipes the JSON input file to the hook via stdin (cat input | hook_script); the official security hook reads sys.stdin and json.loads() it. The stdin JSON for a PreToolUse event has shape: {"session_id":..., "hook_event_name":"PreToolUse", "tool_name":"Bash", "tool_input":{"command":"git push ..."}}. Environment variables that ARE set: CLAUDE_PROJECT_DIR, CLAUDE_PLUGIN_ROOT, CLAUDE_ENV_FILE — but NOT the tool input itself.

Mechanical confirmation (our own test): piping the real-shaped JSON to pre-push-gate-check's stdin with NO positional argument —
  echo '{"tool_name":"Bash","tool_input":{"command":"git push -u origin throwaway"}}' | bash pre-push-gate-check
— returned EXIT 0 (pass-through). The script reads TOOL_INPUT="${1:-}" (positional $1), which is empty under the real invocation method, so it greps an empty string, finds no "git push," and passes through. The script is blind to the command because it reads a channel Claude Code never writes to.

### Why Part J's earlier traces were misleading
When we invoked pre-push-gate-check DIRECTLY with the command as a positional argument (bash pre-push-gate-check "git push ..."), it worked and blocked (exit 1). But that tested a code path Claude Code never uses — Claude Code never passes the command as a positional argument. The script "works" only when manually fed $1, which never happens in production. run-hook.cmd's argument handling is irrelevant because the tool input does not travel through arguments at all — it travels through stdin.

### The real bug
All input-taking gate scripts read tool input from positional $1. They should read JSON from stdin and extract tool_input (for Bash, tool_input.command). They have NEVER been able to see the tool input by any path, because they read positional arguments while Claude Code writes to stdin. This is a more fundamental and cleaner explanation than Part J's argument-forwarding theory.

### The corrected fix (SAFER than Part J's)
Do NOT touch run-hook.cmd. The wrapper is not the problem; leave it alone (this removes the cmd-quoting hazard and the risk of breaking every hook that worried us in Part J).
Instead, rewrite each input-taking gate script to read JSON from stdin and extract the relevant field, then operate on that:
- Read stdin (e.g., raw=$(cat); or jq directly on stdin)
- Parse out tool_input — for Bash gates, tool_input.command; for Write/Edit gates, tool_input.file_path / tool_input.content as appropriate
- Then apply the existing logic (e.g., grep the extracted command for git push)
jq is available (installed earlier this arc at %USERPROFILE%\bin\jq.exe).

Scripts requiring this stdin-JSON rewrite (all four input-taking gates):
- pre-push-gate-check (Bash matcher) — extract tool_input.command, grep for git push
- bootstrap-write-gate (Write/Edit matcher) — extract tool_input.file_path / content
- coupled-edit-gate (Edit matcher) — extract tool_input.file_path
- rubric-validity-gate (Agent matcher) — extract relevant tool_input fields

### Scope note
The fix is SAFER per-edit (bash stdin parsing, no load-bearing wrapper surgery, no cmd-quoting) but BROADER (four scripts, each needing the same stdin-JSON treatment and isolated testing). Each script's rewrite should be verified by piping real-shaped JSON to its stdin and confirming correct block/pass behavior — the same test method that confirmed the bug.

### Verification method (for the fix, reuse)
Per script: pipe real-shaped JSON to its stdin (e.g., echo '{"tool_name":"Bash","tool_input":{"command":"git push ..."}}' | bash <gate-script>) and confirm exit 1 (block) when it should block, exit 0 (pass) when it should pass. Then re-run the end-to-end throwaway-branch push test to confirm the gate blocks a real push with missing evidence.

Only Part J's CAUSE MECHANISM (argument forwarding) and PROPOSED FIX (edit run-hook.cmd) are superseded by this Part K: the real cause is positional-vs-stdin, and the real fix is rewriting the gate scripts to read stdin JSON, leaving run-hook.cmd untouched.
