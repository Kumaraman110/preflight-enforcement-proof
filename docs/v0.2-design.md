# Preflight v0.2 — Design Document

## Status

Draft, in progress. This document captures design decisions as they are made. Sections marked OPEN are not yet designed. Do not implement from this document until it is marked complete.

## Source of this design

This design responds to the PR 12 issues inventory (docs/pr12-issues-inventory.md, commit 5339ee4) and its bucketing (docs/pr12-issues-bucketed.md, commit 1dea5ea). The bucketing found 63% of PR 12 issues are framework structural gaps (Bucket A), 20% are CPSL-specific requirements (Bucket B), 17% are framework-shaped CPSL needs (Bucket C). v0.2 addresses the framework-level work (A + C); Bucket B becomes content teams declare once the framework has somewhere to put it.

## The core reframing

Reading the existing CLAUDE.md (the CPSL team contract, 519 lines) surfaced that the document describes framework enforcement that does not actually happen at runtime. It mandates the Stage 1 gate, the four mechanical hooks, 96% coverage, and a definition-of-done checklist — but PR 12 showed none of these enforced anything. The hooks didn't fire, coverage wasn't gated, the definition-of-done didn't block push. The gap between what CLAUDE.md describes and what the framework does at runtime IS the framework's core problem (this is roll-up r12 from the bucketing made concrete).

Additionally: the existing CLAUDE.md actively contributed to the PR 12 wire-contract failure. Its guidance — "Migrate the intent, not the literal code" and "Optimize during migration: async/await" — licensed the agent to change result codes and alter async semantics, because the document gave modernization guidance with no counterweight requiring external-contract preservation. The agent followed the contract; the contract was incomplete.

v0.2 therefore has two workstreams: (1) make CLAUDE.md's existing enforcement promises real, and (2) add the wire-contract preservation capability the contract is missing.

## Part A — The Team Contract (DESIGNED)

### What it is

A declaration of what a given team's migration requires. Per-team, not per-migration. One contract per consuming team; all of that team's migrations inherit from it. Service-specific details live in the comparison surfaces the contract declares, not in the contract itself.

### Where it lives (DECIDED)

The contract is NOT a separate file. It is a new, high-precedence SECTION added to the existing CLAUDE.md. The existing CLAUDE.md is already designated "the team contract" in its own first line; v0.2 adds the missing wire-contract section to it.

Critical: this new section must have explicit precedence over the existing modernization guidance in CLAUDE.md. Where the wire-contract section conflicts with guidance like "migrate the intent, not the literal code" or "optimize during migration," the wire-contract section wins. The precedence must be stated in the section itself, e.g.: "Where this section conflicts with the modernization guidance elsewhere in this file, this section governs. Modernize implementation freely; preserve external contract exactly."

### The three parts (DESIGNED)

**Part 1 — Success criteria.**

Declarative statements of what must be true at migration completion. Not how to verify — just what must be true. For the CPSL team, the success criterion is wire-format and result-code parity: every result code the legacy emits must appear in migrated output with identical semantics; response messages, payload field names and shapes, HTTP status codes per error condition, and version-based routing behavior must be preserved.

**Part 2 — Comparison surfaces.**

For each success criterion, which legacy artifacts define the truth. For the CPSL wire-parity criterion, the comparison surfaces are the legacy controller PLUS repository PLUS auth filter — the full transitive scope, not just the entry-point controller. (PR 12 failed precisely because discovery read only the controller, 183 lines, and missed the repository, 500 lines, where 80% of the wire contract lives.) Version-based routing logic is a first-class comparison surface for CPSL specifically, because CPSL code is heavy in version-based routing.

**Part 3 — Constraint handling (three-way).**

Every change the migration makes falls into one of three categories, determined by two independent tests:

**PRESERVE EXTERNAL CONTRACT** — things a caller of the API observes. Test (axis 1): "Would a caller's existing code break or behave differently if pointed at the migrated service instead of the legacy service, assuming nothing in the caller is changed?" If YES → preserve exactly. This covers result codes, response messages, payload field names and shapes, HTTP status codes per error condition, version-based routing logic, endpoint URLs and HTTP methods.

**MODERNIZE INTERNAL IMPLEMENTATION** — things a caller does not observe. Same axis-1 test, answer NO → modernize freely. This covers sync/async patterns, fire-and-forget vs await, HTTP client library choices, JSON serialization library, DI container patterns, logging frameworks, exception-handling idioms (as long as external HTTP status + ResultCode behavior is preserved), configuration patterns, test framework choices.

Caveat: JSON library swaps (e.g., Newtonsoft → System.Text.Json) are modernize-freely at the code level BUT require compatibility verification of the produced output, because the two libraries differ subtly in null handling, casing, and date serialization. A library swap is not safe by virtue of being internal; the output must be verified to match.

**SURFACE AS WORK** — an independent axis. Test (axis 2): "Does this change require additional engineering artifacts beyond the application code itself — database schemas, infrastructure, downstream service contracts?" If YES → the framework does the work visibly, producing real artifacts, never placeholders. This is NOT a request for human permission; it is the framework doing the work honestly. A single change can be MODERNIZE-FREELY on axis 1 AND SURFACE-AS-WORK on axis 2 simultaneously (the DB migration is exactly this: invisible to the caller at the wire level, but visible engineering work requiring schema artifacts).

### The framework's job for Part 3 (DECIDED)

The framework must REASON about each constraint and decide correctly — not merely detect-and-flag, not merely preserve-by-default. The framework needs to understand why each constraint exists and what the right call is. This is a deliberately high bar, chosen because the team's position is that the framework must be rock-solid autonomously.

### No human gates (DECIDED)

There is deliberately NO "human-required decisions" part. The team rejected mid-flow human approval gates. The framework must operate end-to-end autonomously. If the framework cannot autonomously preserve external contract and surface additional work correctly, that is a framework defect to fix — not a reason to add a human checkpoint. Visibility into what the framework decided comes through the decisions-log (see OPEN section), not through asking permission.

### The database faithfulness rule (DECIDED)

When persistence-layer migration is needed (e.g., SQL Server → PostgreSQL), the framework must port faithfully with EXACT identifier fidelity: same database name, same table names, same column names, same data types — no modifications, no schema "improvements," no renamed identifiers. The framework navigates the legacy persistence artifacts and produces equivalent target artifacts (e.g., PostgreSQL DDL and PL/pgSQL functions) using identical names.

PR 12 failed this completely: it invented five PostgreSQL stored-function names that exist nowhere, with no DDL, no real extraction. That is the exact failure this rule prevents.

### The legacy-DB-unreachable workflow (DECIDED)

The CLI cannot directly connect to the legacy SQL Server database. Therefore the framework's "surface as work" capability for DB migration has two acceptable modes:

- **Mode 1 (CLI cannot reach legacy DB — the expected case):** the framework produces a precise, concrete artifact listing exactly what must be fetched from the legacy DB — table names, stored-procedure names, column names with data types — formatted as either a runnable extraction script or a step-by-step extraction guide. It hands this to the human, who fetches and returns the output. The framework then converts the returned legacy artifacts to faithful target-DB equivalents.
- **Mode 2 (CLI can reach legacy DB, if such a capability exists):** the framework fetches and converts autonomously in one pass.

Critically: the framework must be HONEST about which mode applies. It must never pretend it performed Mode 2 (autonomous fetch) when it actually cannot reach the DB — that pretense is exactly what produced PR 12's invented function names.

**Derived capability need:** This implies the framework needs a new discovery capability distinct from code-coupling analysis: "legacy data-access surface extraction" — reading the legacy code's data access patterns (SQL strings, stored-proc invocations, ADO.NET parameter declarations) to infer which DB tables/sprocs/columns the service touches, BEFORE it can produce the fetch list. The current discovery-analyst produces a code dependency map (dependency-map.json); persistence-bearing services also need a data-access-surface map. This capability is DESIGNED-IN-PRINCIPLE, implementation OPEN.

## Part B — The Two Workstreams (DECIDED structure, details partially OPEN)

v0.2 splits into two parallel workstreams that reinforce each other:

**Workstream 1 — Make CLAUDE.md's existing promises real.**

The framework already describes enforcement it does not deliver. This workstream makes the description true: the mechanical hooks actually fire, the Stage 1 gate actually gates, the 96% coverage actually blocks push, the definition-of-done actually prevents push when unmet. This maps to Bucket A roll-ups, especially r03 (hooks configured but inert), r04 (no hook observability), r06 (sub-agent architecture partially realized), r15 (discovery output not enforced).

**Workstream 2 — Add the wire-contract preservation capability.**

The framework cannot currently preserve or even detect wire-contract drift. This workstream adds: the three-part contract section in CLAUDE.md (DESIGNED above), spec extraction (OPEN), the parity gate (OPEN), the decisions-log (OPEN), and the DB faithfulness capability (DESIGNED in principle, implementation OPEN). This maps to Bucket C and the roll-ups r01 (team-contract artifact), r02 (spec extraction), r05 (result-code comparison), r07 (done ≠ contract-preserved), r09 (decisions-log).

**Ordering dependency (IMPORTANT):**

The two workstreams can be DESIGNED in parallel, but there is a validation dependency: Workstream 2's parity gate cannot actually fire until Workstream 1's hook-activation work is done. A parity gate plugged into an enforcement layer that doesn't fire would be just as inert as the current hooks. Therefore: hook activation (Workstream 1, r03) is a prerequisite for the parity gate (Workstream 2, r07) to be VALIDATED, even if both are designed concurrently.

## Part C — OPEN design items (NOT YET DESIGNED)

The following are identified as needed but have NOT been designed in the conversation so far. Do not invent designs for these. Record them as open questions to be designed next.

- **Spec extraction (r02).** Given the contract declares "compare wire-format using controller + repository + auth filter," how does the framework actually produce the forensic legacy-behavior spec? What does the spec artifact look like? How is it parameterized by the contract's declared comparison surfaces? This is the next design topic.

- **The parity gate (r07).** Where does it sit in the migration flow? What does it consume (the spec + the migrated output)? What does it block on? How does it report mismatches? How does it plug into the hook-activation machinery from Workstream 1?

- **The decisions-log (r09).** When is it written? What does it capture (every surface-as-work decision, every modernize-freely choice that's non-obvious)? Who/what reads it? What format?

- **Mid-flow surfacing mechanism (r11).** Given there are no human gates, how does the framework make surface-as-work decisions visible during the run rather than only at the end? Is this just the decisions-log, or something more?

- **Hook activation (r03).** Why did the hooks not fire during PR 12 — were they not registered with the Claude Code runtime, did run-hook.cmd fail silently, or something else? This needs root-cause investigation before it can be designed. Mark as REQUIRES INVESTIGATION.

- **Bootstrap's role in contract setup.** Since the contract is per-team and lives in CLAUDE.md, how does the bootstrap skill detect whether a contract section exists, and walk the team through declaring one if not? Not yet designed.

- **Spec extraction for data-access surface.** The "legacy data-access surface extraction" capability (named under the DB faithfulness rule) needs design: how does it read legacy data access patterns and produce a data-access-surface map?

## Part D — Decisions explicitly NOT made

These were considered and rejected or deferred:

- A separate team-contract file was considered and rejected in favor of a section in the existing CLAUDE.md.
- A "human-required decisions" contract part was considered and rejected — the framework must be autonomous.
- Per-migration contracts were considered and rejected in favor of per-team contracts.
