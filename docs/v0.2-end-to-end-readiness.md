### A3. KNOWN LIMITATIONS (state plainly so the run isn't mis-graded)

1. **error_path is ADVISORY.** Its extraction is unreliable on the migrated side (3/5). In the run, error_path deviations appearing only as advisory warnings (or being incompletely extracted) is EXPECTED and CORRECT behavior, not a gate miss. Do NOT grade error_path coverage as pass/fail on completeness.

2. **Pass-through/delegated behavior — partial.** When the downstream emitter is on disk (e.g., TokenManagerDataBaseOperations.cs), chain-following resolves the pass-through value. When the downstream is a black box (collapsed chain, stored proc is the terminal emitter with no extractable source), only the mechanism difference (pass-through vs local `result_determination`) is caught. The actual downstream value is unresolvable from source.

3. **Minor over-extraction tendency.** One migrated run spuriously included E0007 (a ResultMessages lookup-table entry never emitted as a behavior). This is a false positive (lower stakes than a false negative) caused by one agent being overly inclusive about the lookup table. The grading does not penalize over-extraction.

4. **Canonical ID naming variance.** `cc-token-created` vs `token-created` and `token-expiration-extended` vs `token-slid` are legitimate naming variants that produce the same parity outcome (they match cross-side via their suffix). The parity engine matches by exact ID — runs that use different variant names will produce phantom MISSING+ADDED pairs at the parity layer. This is a known ID-stability issue that is cosmetic for completeness grading but consequential for parity noise. The run should note the noise level.

5. **4 UNCERTAIN lib files** (`resolve-config.sh`, `extract-overrides.sh`, `metrics.md`, `proactive-triggering.md`) — referenced only by docs; the end-to-end run is the oracle for whether they're live. If the run succeeds without them being invoked, they're dead code.

## Part B — Safe-Push Mechanics (Resolved)

### How the gate fires

1. `hooks/hooks.json` registers a `PreToolUse` hook with matcher `"Bash"`.
2. Every Bash tool call pipes its JSON to `hooks/pre-push-gate-check`.
3. `pre-push-gate-check` extracts `tool_input.command`, greps for `git push`.
4. If NOT a push → exit 0 (allow). If IS a push → exec `hooks/pre-push-gate`.
5. `pre-push-gate` checks 4 evidence files in `.preflight/gate/`:
   - `tests-pass` (Gate 1)
   - `stage1-clean` (Gate 2)
   - `map-validated` (Gate 3, conditional on dependency-map.json existing)
   - `parity-clean` (Gate 4, conditional on `*/.preflight/*/behavior-spec.json` existing at depth ≤ 3)
6. Each evidence file must exist and contain a `HEAD=` line matching current HEAD or HEAD^.
7. Missing or stale → exit 2 → Claude Code blocks the tool call.

### Gate 4 activation condition

Gate 4 fires ONLY when a behavior-spec baseline is found:
```bash
find . -path "*/.preflight/*/behavior-spec.json" -maxdepth 3
```
If this find returns results → Gate 4 requires `parity-clean` evidence.

### Safe-push options (no commits leave the machine)

| Option | Mechanism | Exercises | Tradeoff |
|---|---|---|---|
| **A. Direct script invocation** | `bash hooks/pre-push-gate` in the project directory with a behavior-spec.json present and NO parity-clean evidence | Gate 4's check logic and exit-2 path | Does NOT exercise the PreToolUse hook chain (hooks.json → pre-push-gate-check → pre-push-gate). Proves the gate script works; doesn't prove Claude Code's hook wiring fires it. |
| **B. Actual `git push` to a local bare repo** | `git init --bare /tmp/test-remote && git remote add test-local /tmp/test-remote && git push test-local HEAD:test-branch` | The FULL hook chain: Bash tool call → PreToolUse fires → pre-push-gate-check detects "git push" → pre-push-gate runs → Gate 4 blocks | Exercises the real code path. Push target is a local bare repo, not origin. No commits leave the machine. If the gate FAILS to block, only a throwaway local bare repo receives the push. |
| **C. Dry-run** | `git push --dry-run origin <branch>` | The PreToolUse hook chain fires (it matches `git push` in the command string, and `--dry-run` is not filtered out by the grep) | Git contacts origin but makes no changes. However: if the gate somehow fails to fire, `--dry-run` still prevents actual push. Belt-and-suspenders. Less clean because it contacts the remote. |

### RECOMMENDED: Option B (local bare repo)

**Rationale:**
- Exercises the full hook chain end-to-end (PreToolUse → matcher → script → gate → exit 2)
- Zero network traffic, zero risk of commits reaching origin
- If gate fails to block, the only consequence is a local temp directory getting commits
- Easy cleanup: `rm -rf /tmp/test-remote`
- The allow path is also testable: write parity-clean evidence, re-attempt push, verify it lands in the bare repo

**Setup:**
```bash
git init --bare /tmp/preflight-test-remote
git remote add test-local file:///tmp/preflight-test-remote
```

**Block test:** Attempt `git push test-local HEAD:test-branch` with behavior-spec.json present and NO parity-clean evidence → expect exit 2 / hook-denied.

**Allow test:** Write parity-clean evidence with current HEAD, re-attempt → expect push succeeds to bare repo.

**Teardown:**
```bash
git remote remove test-local
rm -rf /tmp/preflight-test-remote
```
