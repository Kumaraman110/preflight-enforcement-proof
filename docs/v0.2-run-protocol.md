# v0.2 End-to-End Run Protocol — Examiner's Manual

**Date:** 2026-06-01
**Purpose:** Instructions for a FRESH CLI session to conduct the autonomous end-to-end test of the preflight framework. This is the examiner's manual — it tells the session HOW to run the test without leaking the ANSWERS it's graded against.
**Grading standard:** `docs/v0.2-end-to-end-readiness.md` (Part C). Opened AFTER the run completes, not before.

---

## The Cardinal Rule

> The fresh session conducts the test. The framework's agents do the migration working ONLY from CLAUDE.md + their own discovery. The session must NOT hand-feed scope, the recognition pattern, the comparison surfaces, the downstream emitter location, or any expected deviation.

If the framework cannot derive something from its own contracts and discovery logic, that gap IS a finding — not something to rescue.

---

## Part 1 — The Cold-Start Entry Point

### What the operator invokes

```
/preflight:migrate SessionToken
```

Invoke the framework's cold entry point the way a real engineer would — the bare command, no padded scope, no hand-fed answers.

The routing skill (`skills/routing/SKILL.md`) is loaded at session start by the `session-start` hook. It tells the agent that "start migrating a service" → invoke `/preflight:migrate`. The migrate skill is the cold-start entry point.

### The autonomous dispatch chain

Once `/preflight:migrate SessionToken` is invoked, the framework autonomously executes:

| Step | Actor | Input source | Output |
|---|---|---|---|
| **0. Environment detection** | migrate skill | `.preflight/config.json` in working directory | Config fields: mode, legacyRepoPath, rubric path, branch settings |
| **1. Phase 1 — Discovery** | `discovery-analyst` sub-agent (spawned by migrate) | Legacy repo path from config → locates service files by name matching | Technical debt inventory, readiness score, `dependency-map.json` |
| **2. Phase 1 — Behavioral extraction (legacy baseline)** | `spec-analyst` sub-agent (spawned by migrate) | Dependency map from step 1 OR comparison surfaces from `CLAUDE.md`'s Behavioral Contract section | `behavior-spec.json` (the BASELINE for parity) |
| **3. Phase 1 — Business architecture** | migrate skill | Legacy source + CLAUDE.md team contract | Decoupling assessment, consolidation candidates |
| **4. Phase 1 — Readiness score** | migrate skill | Discovery output | Green/Yellow/Red strategy selection |
| **5. Human gate** | migrate skill | Phase 1 outputs presented to user | User says "go" (or corrects) |
| **6. Phase 2 — Code generation** | migrate skill (may dispatch implementer for coupled groups) | Generation spec + CLAUDE.md + reference service patterns | Migrated service code |
| **7. Post-migration dependency map refresh** | `discovery-analyst` (re-invoked on NEW code) | Migrated service directory | Fresh dependency-map.json |
| **8. Post-migration behavioral extraction (current)** | `spec-analyst` (dispatched by migrate's Behavioral Parity Verification section) | Fresh dependency map + CLAUDE.md Behavioral Contract | `behavior-spec-current.json` for the MIGRATED side |
| **9. Parity diff + Gate 4 evidence** | `lib/parity-check.sh` + `write-gate-evidence parity-clean` (wired in migrate) | Baseline spec + current spec | Parity report (exit 0/1/2); evidence written on exit 0 or 1 |
| **10. Handoff → /preflight:fix-and-close** | migrate skill | Commit-message hint | Stage 1 gate → push → Stage 2 loop |
| **11. Stage 1** | `code-reviewer` sub-agent (spawned by fix-and-close) | Rubric + current diff | CLEAN or NEEDS_FIXES |
| **12. Push** | fix-and-close | Gate evidence (tests-pass, stage1-clean, parity-clean) | Commits reach remote |
| **13. Stage 2** | `external-review-handler` sub-agent | `gh` CLI → GitHub PR → Copilot review | Comments classified, fixes returned, captures written |
| **14. Fix loop** | fix-and-close (dispatches implementer per coupled group) | Copilot findings + coupling map | Clean PR or cap hit |

### NOTE — Steps 8-9 are wired but never executed

As of commit `335ecb4`, `skills/migrate/SKILL.md` explicitly wires the full post-Phase-2 parity chain: migrated-spec extraction (spec-analyst) → parity-check.sh → Gate 4 evidence (write-gate-evidence parity-clean or surface blocking violations to the user). The migrate skill ATTEMPTS this autonomously — no supervisor bridging required.

**However:** steps 8-9 have never been executed in a real run. This blind session is their first live execution. Two outcomes are possible:

1. **Success** — the chain runs end-to-end. This is expected complete-product behavior, not a surprise. Record it as "autonomous success."
2. **Runtime failure** — the wiring exists but fails at execution time (wrong path resolution, missing input, spec-analyst error, script invocation failure). This is a **completion-bug finding** — a defect in the wiring, not a gap for the supervisor to bridge. Record the failure, note exactly where and why it broke, and let the run end where it ends. The fix happens in a subsequent build session, not mid-run.

**The supervisor does NOT rescue a runtime failure in steps 8-9.** There is no "manually invoke the behavior-spec skill to continue" — that was the protocol when the gap was open. Now that the wiring exists, a failure IS the finding.

## Part 2 — Stage 2 Push/Review Target

### What Stage 2 requires

The `external-review-handler` agent needs:
1. A GitHub PR (created via `gh pr create`)
2. Copilot reviewer assignment (`gh pr edit --add-reviewer copilot-pull-request-reviewer[bot]`)
3. GitHub API access (for polling reviews/comments via `gh api`)

These require a **real GitHub remote** — not a local bare repo. Copilot reviews only work on GitHub-hosted PRs where the Copilot reviewer bot has access.

### Options for a safe Stage 2 target

| Option | Setup cost | Risk | Copilot access? |
|---|---|---|---|
| **A. Personal fork of the org repo** | `gh repo fork United-Airlines-Org/cyf.cpsl_core --clone=false` + add as remote | Low risk — fork is under user's account. Push to fork, PR within fork. | YES if Copilot is enabled on the user's account or the fork inherits org settings |
| **B. Throwaway sandbox repo** | Create a new empty repo on the user's GitHub account, push the branch there | Zero risk — repo is disposable. Delete after. | YES if user has GitHub Copilot enabled on their account |
| **C. Existing org repo (real origin)** | Zero setup | HIGH RISK — dumps 60+ commits to the shared repo. FORBIDDEN. | N/A — forbidden |
| **D. Skip Stage 2 entirely** | Zero setup | No risk. Tests Gate 4 + Stage 1 only. | N/A — not tested |

### RECOMMENDATION

**Option B (throwaway sandbox repo)** is the cleanest:
1. User creates a new repo: `gh repo create <username>/preflight-e2e-sandbox --private --confirm`
2. Add as remote: `git remote add sandbox https://github.com/<username>/preflight-e2e-sandbox.git`
3. The fresh session pushes to `sandbox` instead of `origin`
4. PR is created within the sandbox repo
5. Copilot reviews the PR (if user has Copilot enabled)
6. After the run: `gh repo delete <username>/preflight-e2e-sandbox --yes && git remote remove sandbox`

### PREREQUISITE the user must provision BEFORE the fresh session

The fresh session cannot create GitHub repos or configure authentication — that's environmental. The user must:

1. Create the sandbox repo (or fork)
2. Add it as a git remote (name: `sandbox`)
3. Confirm Copilot reviewer access works: `gh api repos/<username>/preflight-e2e-sandbox` returns 200
4. Confirm `gh auth status` shows valid auth with `repo` scope
5. Update `.preflight/config.json` temporarily: set `branch.remote` to `sandbox` (or the fresh session can be told "push to remote `sandbox`" as an environmental instruction)

If the user CANNOT provision a Copilot-enabled sandbox (e.g., no personal GitHub Copilot access), Stage 2 cannot be tested end-to-end. In that case: test through Gate 4 + Stage 1 (still valuable), document Stage 2 as "untestable without Copilot-enabled remote" and move on.

## Part 3 — The Run Protocol

### 3a. THE BLIND CONDITION

The fresh session:
- Invokes `/preflight:migrate SessionToken` — NOTHING ELSE
- Does NOT read `docs/v0.2-end-to-end-readiness.md` (the answer key) until grading
- Does NOT read `.preflight/SessionToken/ground-truth-inventory.md` (the behavioral answer key)
- Does NOT receive any list of "expected deviations" or "things to look for"
- Does NOT receive file lists, scope guidance, or pattern hints beyond what `CLAUDE.md` and `.preflight/config.json` already contain (those are the framework's own contracts — reading them is not bias)

The session IS told (environmental setup, not answers):
- "Push to remote `sandbox` (not origin)" — this is routing, not content
- "The legacy repo is at the path in `.preflight/config.json`" — this is config, already there

### 3b. SETUP vs RESCUE — The Line

**ALLOWED (environmental setup — removes blockers so the framework gets a fair run):**
- Provisioning the sandbox remote and configuring auth
- Telling the session which remote to push to
- Providing `gh` auth credentials
- Starting the session in the correct working directory
- Invoking the entry point (`/preflight:migrate SessionToken`)

**FORBIDDEN (rescue — leaks answers or masks framework deficiencies):**
- Telling the session which files are in scope (the framework must derive this)
- Telling the session what result codes to expect
- Restating, hinting at, or paraphrasing any specific deviation from the readiness doc (`docs/v0.2-end-to-end-readiness.md`) — not the result-code changes, not the wire-contract changes, not the side-effect changes, in any frame including "forbidden" examples. The 17 graded deviations live ONLY in the readiness doc, consulted at END for grading. This protocol must contain ZERO of them.
- Fixing a wrong-scope decision the framework made
- Correcting a spec-analyst extraction that missed behaviors
- Intervening when Stage 1 or Stage 2 finds something the framework should have caught (or missed something it should catch)
- Manually writing gate evidence to bypass a failing gate
- Editing the rubric mid-run to make Stage 1 pass

**THE PRINCIPLE:** If the framework's LOGIC produced the outcome, it stands — good or bad. If the framework's ENVIRONMENT prevented it from running at all (no auth, wrong remote, missing tool), that's setup. The supervisor records stumbles as findings; it does not fix the framework's path.

### 3c. SAFETY BOUNDARIES

The supervisor HARD-STOPS ONLY:
- Any `git push` to `origin` (the real org remote) — redirect to `sandbox`
- Any destructive operation on shared branches (`git reset --hard`, `git push --force` to AccountLookUp_POC/main)
- Any `gh` operation against the org repo that creates/closes/merges PRs or issues
- Any write to the legacy repo root (`C:\Users\v173617\Source_Code\CTIAPI-DEV_Work` — NOT the migration-root's `CTIAPI-DEV_Work/` subdirectory)

Everything else — including wrong fixes, missed findings, loops, cap hits, stuck states — the framework does on its own. Safety enforcement is not rescue.

### 3d. THE FULL RUN

**Phase 0 — Session start:**
1. Open a FRESH Claude Code session in `C:\Users\v173617\Source_Code\CPSL_Migration_POC_temp`
2. Confirm: `preflight active | mode=migration` appears in session context (session-start hook fires)
3. Type: `/preflight:migrate SessionToken`

**Phase 1 — Discovery + Extraction (autonomous):**
4. Framework discovers legacy service (from `migration.legacyRepoPath` + service name matching)
5. Framework spawns discovery-analyst on legacy code → dependency map
6. Framework spawns spec-analyst on legacy code → behavior-spec.json (the BASELINE)
   - OBSERVE: Does it find the downstream emitter (declared in CLAUDE.md's comparison surface 7) via the dependency map or CLAUDE.md surfaces? Or does it miss it?
   - OBSERVE: Does it produce a complete behavior-spec (all result codes, side effects, state transitions)?
7. Framework assesses readiness, presents Phase 1 to user
8. User says "go"

**Phase 2 — Code generation (autonomous — OR the session recognizes the code already exists):**
9. The migrated code already exists on `pr12/sessiontoken-experiment`. The framework should detect this (e.g., the branch exists, or the service folder has source on that branch). If it offers to resume from post-Phase-2, accept.
   - If it does NOT detect existing code (because we're on AccountLookUp_POC, not pr12): the supervisor tells it "the migrated code is on branch pr12/sessiontoken-experiment — check it out or use git show to read it." This is environmental routing, not rescue — the code's location is a fact, not an answer.

**Phase 2.5 — Post-migration extraction + parity (wired, first execution):**
10. After the framework completes Phase 2 (or recognizes it's done), the migrate skill's "Behavioral Parity Verification" section dispatches spec-analyst on the MIGRATED code autonomously.
    - OBSERVE: Does it invoke spec-analyst? Does it resolve the correct migrated source path from the fresh dependency map?
    - If it FAILS at runtime (wrong path, agent error, missing input): record as a completion-bug finding. Do NOT rescue — the run ends where it ends.
11. Framework runs `parity-check.sh` with baseline vs current.
    - OBSERVE: What exit code? What violations? How many blocking?
12. If blocking violations → the framework should report them and present Fix/Accept/Investigate options. If it attempts to write `parity-clean` evidence despite blocking violations → that's a finding (it shouldn't do that). If it fails before reaching parity-check → completion-bug finding (see NOTE above).

**Phase 3 — Stage 1 + Gate 4 (autonomous):**
13. Handoff to `/preflight:fix-and-close`
14. Stage 1 code-reviewer walks the rubric against the diff
15. Gate 4 checks for parity-clean evidence
    - OBSERVE: Does it block? Does the block message name parity?
16. Stage 1 fixes (if any) → re-run → clean
17. Push to `sandbox`

**Phase 4 — Stage 2 Copilot loop (autonomous, if sandbox is provisioned):**
18. PR created on sandbox repo
19. Copilot reviewer assigned
20. Poll → comments → classify → fix → re-push → poll
21. Terminal state: SUCCESS, CAPPED, STUCK, or BLOCKED

**Terminal state reached.** The run is complete.

### 3e. OBSERVE-AND-RECORD

At EVERY step, the supervisor (user watching the fresh session) records:

| Category | What to note |
|---|---|
| **Autonomous success** | Framework derived something correctly without help (found the emitter, scoped the files, caught a deviation) |
| **Gap / stumble** | Framework needed something it didn't have, or made a wrong judgment call (mis-scoped, missed a file, wrong fix) |
| **Environmental block** | Framework couldn't proceed for non-logic reasons (no auth, wrong remote, missing tool) |
| **Bias risk** | Any point where the supervisor provided information that could have influenced the framework's logic |

The gaps are the VALUE of the run — they tell us exactly what the framework is missing for the next iteration.

### 3e.1. OBSERVED TEST POINT — Root Disambiguation

Two directories share the name `CTIAPI-DEV_Work` in DIFFERENT roots:

- **LEGACY (read-only, never modify):** `C:\Users\v173617\Source_Code\CTIAPI-DEV_Work`
- **MIGRATION-ROOT (working):** `C:\Users\v173617\Source_Code\CPSL_Migration_POC_temp\CTIAPI-DEV_Work`

The framework must resolve its own roots from config (`migration.legacyRepoPath`) and discovery output. The supervisor does NOT pre-qualify paths in the invocation prompt and does NOT correct path handling mid-run.

**WATCH:** Does the framework distinguish the legacy input root from the migration working root on its own? If it confuses them (reads from the wrong root, writes to the legacy root, scopes the wrong directory for extraction), RECORD it as a finding — do not fix it.

The supervisor's ONLY path duty is the safety hard-stop on any WRITE to the legacy root (per 3c).

### 3e.2. OBSERVED TEST POINT — Service Rename Derivation

A migration may rename the service; the legacy and migrated counterparts may carry different names. The framework must DERIVE any such rename from its own discovery + CLAUDE.md contract (comparison surfaces, downstream contract declarations). The supervisor and this protocol do NOT resolve the mapping.

**WATCH:** Does the framework identify the legacy predecessor of the renamed migrated service on its own? Record success or failure as a finding.

**CRITICAL:** This protocol does NOT state that any specific legacy service is the same service as the migration target. The protocol names the migration TARGET as the task (because that's what the engineer types), but must NOT leak the legacy-name → migrated-name equivalence — that is the answer the run is testing.

### 3f. GRADING — SEPARATED FROM DOING

**During the run:** The fresh session does NOT open `docs/v0.2-end-to-end-readiness.md`. It does NOT know the 17 must-catch deviations or the 7 fail conditions. It runs blind.

**After the run reaches a terminal state:**

1. Open `docs/v0.2-end-to-end-readiness.md` (Part C)
2. Collect the parity report the framework produced
3. For each C2 must-catch deviation: verify it appears in the report as blocking. Check all 17.
4. Verify fail conditions F1–F7 are not triggered
5. Confirm Gate 4 blocked when evidence was absent
6. Confirm error_path findings (if any) are advisory, not blocking
7. Document: total blocking violations found, total advisory, any false positives, any noise from ID-naming variance
8. Final verdict: PASS (all C2 items caught, no F-conditions triggered) or FAIL (with specific F-condition and missing item)

The grading step references the criterion doc — it does NOT restate the 17 deviations here (so reading THIS protocol before the run doesn't leak the answer key into the doing-context).
